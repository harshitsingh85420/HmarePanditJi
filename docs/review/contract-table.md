### 3.3 status-enum — **GENERIC GUARD: YES for Prisma enums, NO for `String` pseudo-enums**

Two guards, and **the second is the one that matters**:

```ts
// A. MEMBERSHIP — every literal compared/assigned to an enum column is a member.
//    Parse schema.prisma enums; scan TS for `status === "X"`, `status: "X"`,
//    `<option value="X">` inside a *Status filter, zod .enum([...]) for a *Status field.
//    → fails on PENDING (admin Override Status, page.tsx:434) and "PAID" (bookings/[id]:159).

// B. WRITTEN-SET vs READ-SET  ← the high-value one
//    WRITTEN(col) = every literal assigned to `col` inside a prisma create/update/upsert.
//    READ(col)    = every literal compared against `col`, or sent as a filter value for it.
//    ASSERT READ ⊆ WRITTEN ∪ {schema default} ∪ explicit LEGACY allowlist.
```

Guard **B** is what catches the whole family of "legal enum member that no code ever writes":
- **admin cancel guard** `admin.routes.ts:70` reads `REQUESTED`/`ACCEPTED`; `WRITTEN(Booking.status)` = `{CREATED, PANDIT_REQUESTED, CONFIRMED, COMPLETED, CANCELLED, CANCELLATION_REQUESTED, …}` → fails.
- **Booking Monitor filter** `bookings/page.tsx:148-149` → same failure, plus a `WRITTEN \ READ` report would flag *"`PANDIT_REQUESTED` is written but no filter option offers it"* — which is the actual ops complaint.
- **`dashboard-stats` `PENDING`** (`admin.controller.ts:40`) — `PENDING` *is* written (registration), so B alone passes it. **Hand-pin required:** extend `kycContract.test.ts` §D's pinned-file list to include `services/api/src/controllers/admin.controller.ts`, and assert every `verificationStatus` filter in the API uses `KYC_REVIEW_QUEUE_STATUSES` rather than a literal. **This one omission is exactly why sighting #4 survived at a second site — fix the pin list, not just the line.**
- **`paymentStatus === "PAID"`** — caught by A.

**Cannot be generically guarded: `Notification.type`.** It is a `String` column (`schema.prisma:625`) with the intended vocabulary living only in a **comment**, and three competing vocabularies in code. There is no schema truth for a guard to compare against. The fix *is* the guard: promote it to a Prisma enum (or a single exported const union in `packages/types` that both `notification.service.ts` and the reader import), after which guards A and B apply automatically. Say this plainly to whoever picks it up — writing a bespoke test here is wasted work.

### 3.6 id-type — **GENERIC GUARD: NO. Say so plainly.**

`userId` and `panditProfileId` are both `String` at every boundary — nothing textual distinguishes them, so no scanner can tell a correct `panditId` from an incorrect one. **This class turned up 1 break in 10 contracts checked, and the one break is not actually an id confusion** — `authRequest.user?.panditId` reads a property that does not exist on `UserPayload` (`auth.ts:17-23`), which is a *type* failure hidden by a loose `authRequest` cast. - **The other nine contracts are genuinely clean** and there is nothing to guard. Sighting #3 (`Review.revieweeId`) is the historical instance, and it re-verified as agreeing.
- **The only real mitigation, if you ever want one:** branded/nominal types in `packages/types` (`type UserId = string & {__brand:'UserId'}`, `type PanditProfileId = string & {__brand:'PanditProfileId'}`) threaded through the Prisma client's return types. That is a multi-day refactor. Given 9-of-10 agreement, **my recommendation is not to do it** — spend the time on §3.5(iii) and §3.2 instead, which each cover 5+ live breaks.
